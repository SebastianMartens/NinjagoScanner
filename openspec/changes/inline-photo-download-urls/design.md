## Context

See proposal.md - Why for the motivation and the trace that led here. Summary of the current shape being replaced:

- `PictureScannerGrpcService.ListCards` walks the S3 bucket via `photoStore.ListPhotoIdsAsync` (paginated `ListObjectsV2`) to discover photo IDs, then calls `sidecarCache.GetAsync(photoId, ...)` per photo — a DynamoDB `GetItem` per cache miss.
- `PictureScannerGrpcService.GetPhotoDownloadUrls` (the batch RPC from `2026-08-25-batch-photo-download-urls`) takes that same photo ID list from the Web caller and, per photo, awaits `photoStore.ExistsAsync` (an S3 `GetObjectMetadataAsync` HEAD request) before signing a URL with `photoStore.CreateDownloadUrlAsync` (local HMAC signing via `s3Client.GetPreSignedURLAsync`, no network call).
- `SidecarCache`/`SidecarTable` already has `ListAllAsync`, a paginated DynamoDB `Scan` used by the bulk `Scan`/`MigrateSidecars` RPCs, that reads every sidecar record in a handful of page round trips instead of one `GetItem` per photo.

## Goals / Non-Goals

**Goals:**
- Make `ListCards`' response time for download-URL resolution independent of photo count (a small constant number of storage calls, not one-plus-one per photo).
- Remove the now-redundant per-photo S3 existence check that the batch RPC performs on data `ListCards` already has.

**Non-Goals:**
- Changing pre-signed URL expiry (`PhotoStore.DownloadUrlLifetime`, 1 hour) or S3 access patterns beyond generating URLs at a different call site.
- Caching resolved download URLs across requests (e.g. in `SidecarCache`) — each `ListCards` call still signs fresh URLs for the photos it returns. Signing is local and cheap (no network call), so this isn't a cost worth optimizing further right now.
- Changing how `UploadPhotoAsync`'s single freshly-uploaded photo gets its download URL — it keeps using the singular `GetPhotoDownloadUrl` RPC, since it has exactly one photo ID and hasn't just listed it via `ListCards`.
- Fixing the pre-existing drift in `picture-service-card-listing`'s main spec, which still describes a file-system-backed implementation (directories, sidecar files on disk) predating the S3/DynamoDB migration. This change adds requirements about the new `download_url` field and bulk-read behavior without touching that stale framing — reconciling it is a separate, unrelated cleanup.

## Decisions

- **Resolve existence and sidecar data via bulk reads inside `ListCards`, rather than keeping a second RPC.** `ListCards` already gets the authoritative list of existing photo IDs from its S3 listing — a photo ID appearing in that listing *is* the existence check, so a follow-up `ExistsAsync` per photo (as the batch RPC does today) is pure redundant network cost. For sidecar data, add `SidecarCache.WarmFromStoreAsync` — a paginated DynamoDB scan (reusing `sidecarTable.ListAllAsync`) that fills in any not-yet-cached entry via `TryAdd`, leaving an already-cached entry untouched — and call it once at the start of `ListCards`, before the per-photo `sidecarCache.GetAsync` loop that already existed. `GetAsync` still serves from cache first, so after the warm, only photos with no sidecar at all (never scanned) fall through to an individual read. This was a correction mid-implementation: the first pass used `SidecarCache.ListAllAsync` directly (which unconditionally overwrites `entries[photoId]` as it scans) and built a local dictionary — that breaks `PictureScannerGrpcServiceSidecarCacheConsistencyTests`, which proves a value written through the cache (e.g. by `UpdateReviewStatus`) stays visible to a subsequent `ListCards` call even if the underlying store has since diverged out-of-band. `TryAdd`-based warming preserves that "cache wins over store" guarantee while still turning the common case into a small, bounded number of storage calls. Considered keeping the batch RPC and just dropping its `ExistsAsync` call (trusting the caller's photo ID list) — rejected because it still leaves two round trips from Web where zero-extra is achievable, and because a Web-side call site with a stale photo ID list (e.g. built earlier, before a delete) would then get an unsigned/broken URL for a since-deleted photo with no clear failure signal, whereas folding into `ListCards` sidesteps that staleness window entirely by construction.
- **Remove the batch RPC rather than leave it unused.** Once `GetReviewGroupsAsync`/`GetCardsAsync` reads `entry.DownloadUrl` directly, nothing in this repo calls `GetPhotoDownloadUrls`/`GetDownloadUrlsAsync`/`ToCardListItemsAsync` any more (verified — see proposal.md Impact). The repo's stated convention is to delete unused code rather than keep it "just in case."
- **`GetGalleryCardsAsync` and `BuildCardPhotosAsync` read `entry.DownloadUrl` instead of calling the singular `GetPhotoDownloadUrl` RPC per matched photo.** Both already call `ListCardEntriesAsync` (which now returns entries with `DownloadUrl` populated) before their existing per-photo `GetDownloadUrlAsync` call; once the field is present, that follow-up call is redundant for these two call sites too. This wasn't the reported bottleneck (both are bounded to a small number of photos), but it falls directly out of giving `CardEntry` a `download_url` field, so fixing it in the same change avoids leaving an inconsistency where two call sites keep making a request the field was specifically added to avoid.
- **`GetCollectionOverviewAsync`, `GetSeriesSummaryAsync`, and the outer `ListCardEntriesAsync` call in `GetCollectionCardDetailsAsync` are left unchanged.** They only use `photoEntries` for counting/grouping/matching and never touch a download URL. Since signing every entry's URL is local and cheap, `ListCards` doing it unconditionally for all callers (including these three, which will simply ignore the new field) isn't worth special-casing.
- **`CardEntry.download_url` is added as a new field on the existing message rather than a new response wrapper.** Additive proto change, consistent with how the prior batch-URL change added its messages; every existing `CardEntry` consumer keeps working unchanged and gets the field for free.

## Risks / Trade-offs

- [Removing `GetPhotoDownloadUrls` is a breaking gRPC contract change] → No caller of it remains anywhere in this repo once this change lands (confirmed by tracing all callers); if some future external caller needed batch resolution, `ListCards` now serves that purpose directly.
- [`ListCards` now always signs a URL per entry, even for callers that don't use it (Overview, Series Summary)] → Presigning is local HMAC signing against already-loaded credentials, not a network call, so the added cost per unused entry is negligible even at hundreds of entries.
- [A bulk sidecar read inside `ListCards` could silently let a stale/overwritten store value clobber a value just written through the cache] → Mitigated by construction: `SidecarCache.WarmFromStoreAsync` uses `TryAdd`, never overwriting an already-cached entry, and `ListCards` still reads each photo through `SidecarCache.GetAsync` (cache-first) rather than from a raw scan result. Covered by the existing `PictureScannerGrpcServiceSidecarCacheConsistencyTests`, which this change keeps passing unmodified.
- [Both `.proto` copies must be kept in sync manually] → Same existing repo convention as the prior batch-URL change; update both in the same change, covered in tasks.md.

## Migration Plan

Not additive-only this time, since a caller-visible RPC is removed — but still a single-repo, same-deploy-ordering rollout: PictureService must deploy first (adds `CardEntry.download_url`, removes `GetPhotoDownloadUrls`), then Web (stops calling the removed RPC, starts reading the new field). If Web deployed first here, it would fail to compile/run against its own already-updated proto copy expecting `download_url` and no longer having a client method to call — so in practice this is enforced by deploying from the same commit's build artifacts in the correct service order, same as the prior change. No data migration. Rollback is redeploying the previous image of whichever service regressed; rolling back Web alone (to code that still calls `GetPhotoDownloadUrls`) after PictureService has already been rolled back would break the review page, so if a rollback is needed, roll back Web first, then PictureService.
